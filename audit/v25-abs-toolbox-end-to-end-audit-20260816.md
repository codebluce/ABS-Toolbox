# ABS 工具箱端到端专项审计报告

- 审计日期：2026-08-16
- 审计范围：数据更新、数据面板、综合看板融合、静态站点构建、客户端加密门禁、GitHub Pages 发布
- 审计性质：专项工程审计，不属于 `audit/README.md` 定义的 A/B/C 正式送审轮次
- 审计方式：静态代码复核、单元测试、冒烟测试、最小边界复现、产物体积与本机耗时测量
- 总体结论：**NEEDS_REVISION**。主链路可运行，历史重复预处理瓶颈已基本修复；但发布门禁、分支同步、可选模块导航和综合链路测试仍需加固。

## 1. 执行摘要

当前工程已形成完整链路：定稿台账及补充数据源 → 共享 Excel 预处理 → 各面板计算与渲染 → 综合 HTML 拼接 → 明文或加密站点包 → 临时 worktree 更新 `gh-pages`。主流程结构清晰，`compute_data` 与 `render_body` 的分层、共享临时文件注入、protected 模式不发布明文归档等设计值得保留。

本次共识别：

- P1：3 项，涉及错误页面被继续发布、陈旧发布分支、静态门禁安全边界。
- P2：6 项，涉及空 Tab、文件误选、浏览器兼容、参数语义、测试覆盖和运行目录依赖。
- P3：6 项，涉及重复导入、临时文件、HTML 转义、全局前端命名、文档漂移和产物可追溯性。

建议在下一次对外发布前完成 P1；P2 应进入近期迭代，尤其是综合链路自动化测试与可选模块导航修复。

## 2. 端到端链路与审计结论

1. 数据入口：自动选择或显式传入 2026 定稿台账，并可附加 2024/2025 历史台账、消金双源和同业发行数据。
2. 数据预处理：`preprocess_xlsx_for_pandas` 展开合并单元格并生成共享临时工作簿。
3. 面板计算：定价、成本、利差、投资台账、机构画像及可选面板分别计算数据。
4. 页面融合：各模块返回 body/CSS/JS，由综合看板生成器拼成一级、二级 Tab 页面。
5. 结构检查：生成后检查 panel 数和切换函数是否存在。
6. 站点构建：明文模式复制最新页面和归档；protected 模式执行 gzip、PBKDF2-SHA256、AES-256-GCM 并生成浏览器解锁壳。
7. 发布：检查主工作树，创建临时 worktree，替换 `gh-pages` 内容、提交并按参数推送。

链路完整，但第 5 步目前不是阻断门禁，第 7 步也未持续同步远端发布分支。这两处是当前最重要的可靠性缺口。

## 3. 已确认改善与正向设计

### 3.1 共享预处理已消除主要重复 I/O

`gen_integrated_dashboard.py` 只创建一次共享预处理文件，并将 `preprocessed_path` 注入定价、成本、利差、投资台账和机构面板，最终在 `finally` 中清理。历史报告所述“同一 Excel 重复预处理约 9 次”不再是当前事实，不应继续作为未修复缺陷。

### 3.2 数据失败策略已有分层

- 显式启用的消金和同业发行面板失败时直接阻断，避免静默发布错数。
- 理财子、非标额度和授信额度作为非核心可选展示，失败时降级为占位页。
- 共享临时文件进入计算前会检查关键列、列数和有效数据行，可防止部分静默错数。

### 3.3 protected 站点未写入密码或明文看板

实现使用随机 salt/IV、PBKDF2-SHA256 310,000 次、AES-256-GCM 和 gzip；密码只参与本地派生，不落盘。protected 模式不复制明文 archive，基本满足“静态文件泄露时提高离线读取成本”的目标。

### 3.4 worktree 清理与主分支防护合理

发布前检查主工作树是否干净，发布过程在临时 worktree 中完成，并在 `finally` 中清理。相比直接切换分支和覆盖工作区，该设计更安全。

## 4. P1 问题：发布前必须修复或明确接受

### P1-01 综合看板结构 QC 不阻断发布

**证据**：生成器在 panel 数或切换函数异常时仅打印 `[QC WARN]`，随后正常退出。发布脚本只检查子进程退出码，因此仍会组装并发布异常页面。

**影响**：页面结构回归、Tab 脚本丢失或 panel 数错误可能进入 Pages；现有冒烟测试也不识别 `[QC WARN]`。

**建议**：将结构校验抽成纯函数并返回问题列表；失败时删除或不替换正式输出，并以非零退出。部署脚本应显式验证生成产物、manifest 和关键页面结构。

### P1-02 已存在的本地 `gh-pages` 不与远端同步

**证据**：发布逻辑仅在本地分支不存在时 fetch；若本地分支已存在，直接创建 worktree 并推送。

**影响**：本地分支陈旧时可能产生非快进失败，或基于过期历史形成错误发布基线。多人或多设备发布时风险更高。

**建议**：发布前始终 fetch；校验本地与远端关系。推荐从 `remote/gh-pages` 创建一次性 detached worktree，再生成提交并推送；遇到分叉必须中止，不自动覆盖。

### P1-03 静态密码门禁不能等同服务端鉴权

**证据**：站点包含全部密文、salt、IV 和迭代次数，任何访问者均可离线尝试口令；没有身份、撤销、审计、限速或账号锁定能力。

**影响**：弱密码会直接削弱保护；URL 或站点包泄露后无法阻止离线暴力破解，也不能追踪访问主体。

**建议**：在文档和页面中明确其为“客户端加密”，不是鉴权系统。强制高熵口令并建立轮换流程；若数据敏感度要求身份控制，应迁移到 Cloudflare Access、反向代理鉴权或受控内网站点。

## 5. P2 问题：近期迭代

### P2-01 可选数据未提供时仍生成空一级 Tab

`MODULES` 固定包含“资产大盘”和“同业发行”，但相应 panel 只在传入数据时追加。最小复现已确认两项一级 Tab 存在且内容为空。

**建议**：从实际 `panels` 推导一级模块；只有至少一个 panel 时才渲染 Tab 和二级容器，并增加无可用模块的兜底页。

### P2-02 按修改时间选择最新文件可能误选业务旧数据

台账和看板均通过 mtime 选择；人工复制、解压或触碰旧文件会改变 mtime。生成页面后又重新扫描目录，没有直接使用明确的输出路径。

**建议**：优先解析受控文件名中的业务日期，并校验文件内日期；生成器显式接收输出路径，部署脚本直接使用该返回产物。长期建议引入 manifest，记录源文件哈希、业务日期和生成时间。

### P2-03 `DecompressionStream` 无兼容回退

不支持该 API 的浏览器会直接失败，错误信息还将“密码错误”和“不支持解密”合并，难以定位。

**建议**：声明兼容矩阵；引入轻量 gzip 回退库，或在解锁前独立检查并展示明确错误。至少覆盖目标桌面和移动浏览器的真实测试。

### P2-04 `--no-push` 仍创建本地提交

参数帮助已说明“本地更新 commit”，但名称容易被理解为纯预览；执行后本地发布分支状态会变化。

**建议**：拆分为 `--build-only`、`--commit`、`--push`，默认只构建；或保留现状但增加醒目确认和最终摘要。无文件变化时也无需为了“确保同步”无条件 push，可先比较远端引用。

### P2-05 自动化测试未覆盖综合看板与发布核心

当前冒烟测试仅覆盖三个基础报告，不覆盖：可选模块组合、空 Tab、结构 QC、protected 壳、错误密码、站点包明文泄露、manifest、worktree 分支关系。

**建议**：优先补纯函数级测试，不必模拟真实 GitHub：

- 各模块组合的 Tab/panel 一致性。
- QC 异常必须非零退出。
- protected 包不包含源 HTML 特征和明文 archive。
- 正确/错误密码解密验证。
- `publish_to_pages` 的无变化、分叉和 no-push 行为。

### P2-06 测试依赖当前工作目录

从仓库根目录运行标准库测试会因顶层导入失败；切换到 `scripts/` 后 41 项测试通过。

**建议**：将 `scripts` 包化并使用包内导入，或统一测试入口设置 `PYTHONPATH`。CI 应固定从仓库根目录运行，避免“本机可过、流水线失败”。

## 6. P3 问题：代码与维护性优化

1. `peer_issuance_panel` 重复导入，应删除；综合看板函数注释仍描述旧模块数量，应同步实际结构。
2. 预处理临时文件建议用 `tempfile.mkstemp` 或 `NamedTemporaryFile`，并以 `try/finally` 确保工作簿在 save 异常时也关闭。
3. 明文 archive 索引直接拼接文件名和日期，建议使用 `html.escape` 和 URL 编码，避免未来非受控文件名引入 HTML 注入。
4. 多面板 CSS/JS 内联且共享全局命名空间，`selectSub` 等逻辑应限制在当前模块容器；逐步引入命名空间或模块化构建，降低跨面板冲突。
5. `SKILL.md` 的 Skill 名称、版本、Python 版本及路径说明与当前环境和审计记录可能漂移，应建立单一版本来源并在发布前校验。
6. 综合看板默认按天命名，同日多次生成会覆盖。若需审计追溯，应增加时分秒、源数据业务日期或内容哈希；若刻意只保留 latest，应在 manifest 记录前一版本。

## 7. 冷启动与冷加载评估

本次对现有综合看板和 protected 入口进行本机测量：

| 指标 | 实测结果 |
|---|---:|
| 原始综合 HTML | 6,859,653 bytes |
| gzip 后 | 429,969 bytes |
| AES-GCM 密文 | 429,985 bytes |
| 估算 base64 密文 | 573,316 bytes |
| 实际 protected `index.html` | 578,738 bytes |
| gzip 耗时 | 0.0357 秒 |
| PBKDF2 310,000 次 | 0.0264 秒 |
| 内存构建 protected 壳 | 0.0704 秒 |

### 判断

网络体积不是最严重瓶颈：gzip 压缩率约 93.7%，protected 首包约 565 KiB。更值得关注的是解锁后的客户端峰值：base64 字符串、密文字节、解密后 gzip 字节、6.86 MB HTML 字符串、`srcdoc` 和完整 DOM 可能同时存在。低内存移动设备或旧浏览器上的耗时和峰值会明显高于本机 Python 测量。

### 优化顺序

1. 先做真实浏览器基准：入口下载、PBKDF2、解密、解压、`srcdoc` 赋值、DOMContentLoaded、首个 panel 可交互、峰值内存。
2. 延迟初始化非首屏 panel，避免所有图表和筛选器同时执行。
3. 将投资台账等大 JSON 按年份或模块拆分；若必须保持单文件加密，可在解锁后按需解析数据，而非一次构建全部 DOM。
4. 减少重复 CSS/模板和大段内联数据；构建阶段生成体积预算，超过阈值即告警或阻断。
5. 若采用多资源拆分，protected 模式需要同步设计资源加密和加载协议，不能简单暴露明文 JSON。

## 9. 分阶段修复路线

### 阶段 A：发布门禁

1. QC 失败非零退出，部署脚本阻断异常产物。
2. 发布前 fetch 并验证远端分支关系。
3. 明确客户端加密边界和强口令要求。
4. 增加 protected 包明文泄露检查。

### 阶段 B：正确性与可测试性

1. 一级 Tab 按实际 panel 动态生成。
2. 用业务日期或 manifest 选择产物。
3. 从仓库根目录统一执行测试。
4. 补综合看板、站点构建和发布分支测试。

### 阶段 C：性能与维护性

1. 采集真实浏览器时序和内存基线。
2. 延迟初始化非首屏模块，评估大 JSON 拆分。
3. 收敛全局 CSS/JS 命名空间。
4. 清理重复导入、陈旧注释和文档版本漂移。

## 10. 验收标准

- 任一结构 QC 失败时，生成和发布均返回非零且不覆盖上一版。
- 无消金/同业数据时不出现对应空 Tab；启用时 Tab 与 panel 一一对应。
- 发布基线与远端 `gh-pages` 一致；分叉时明确中止。
- protected 站点包不含明文看板和源 Excel，错误密码无法解密，目标浏览器均可解锁。
- 所有测试可从仓库根目录一条命令运行，覆盖核心模块组合和站点构建。
- 建立浏览器性能预算；至少记录首包、解锁、首屏可交互与峰值内存，并在后续版本中防止回退。

## 11. 最终结论

工程主链路已经具备可用基础，且共享预处理显著改善了生成性能；protected 静态包的网络体积也处于可接受范围。当前不建议把精力优先投入微小代码压缩，而应先补齐“错误产物阻断、远端分支一致性、动态模块导航、综合链路测试”四项可靠性基础。完成 P1 并验证后，可进入受控发布；完成 P2 后再开展前端按需加载和内存优化，收益更稳定。
